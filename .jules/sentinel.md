## 2024-08-16 - CORS Configuration and WebSocket Origin Validation
**Vulnerability:** The `serve.py` uses websockets to serve HTTP paths and websockets connections. While `cors: bool` controls `Access-Control-Allow-Origin` on the HTTP endpoints (like `/`), it does not validate the `Origin` header for incoming WebSocket connections. Furthermore, setting `Access-Control-Allow-Origin: *` when `cors=True` can be overly permissive if sensitive data is served or credentials are included.
**Learning:** Websockets are not protected by CORS policies enforced by the browser. If the server does not validate the `Origin` header during the WebSocket handshake, any website can connect to the WebSocket server using JavaScript. This is equivalent to Cross-Site WebSocket Hijacking (CSWSH), similar to CSRF.
**Prevention:** In `process_request` (which handles the HTTP upgrade request for websockets in the `websockets` library), check the `Origin` header. If `cors=False` (default), only allow same-origin requests (e.g. from `resolved_host` / localhost) or deny explicitly cross-origin requests. If `cors=True`, we might allow it, but we should at least warn about `*`. But the primary issue is missing CSWSH protection.
